## 2 目标 范围与使用环境

### 2.1 项目目标

系统目标：让客户找到适合自己需求的医疗资源，并在购买平台服务后，获得持续的诊疗协助；让客服、陪诊师和其他履约人员围绕同一订单协同完成服务。

“上下文一致”应指同一份有效业务事实、明确的更新时间和变更历史。不同角色仍应只看到完成工作所需的信息。

| 目标 | 建议衡量指标 | 口径与待定项 |
|---|---|---|
| 找到可用资源 | 搜索有效结果率、详情到咨询或购买转化率 | 有效结果定义、目标值待定 |
| 顺利购买服务 | 支付成功率、重复扣款数 | 支付成功按支付机构确认；重复扣款目标为零 |
| 持续完成服务 | 阶段按时完成率、异常响应时长 | 以任务到期时间和首次人工响应时间计算 |
| 减少重复沟通 | 资料重复录入率、客户纠错率 | 需定义埋点与统计窗口 |
| 保持信息质量 | 已过期资源比例、纠错处理时长 | 按审核日期和更新期限判断 |
| 客户体验 | 反馈响应率、满意度、投诉闭环时长 | 调查时机与量表待确认 |

### 2.2 已确认范围与服务边界

首版包含完整资源检索与陪诊闭环，以及 AI 答疑查询、OCR、客服代操作、任务与攻略更新、自动提醒和地接。登录已经实现，本轮不重新设计，作为现有依赖复用。

| 事项 | 已确认要求 | 仍需细化 |
|---|---|---|
| 目标市场 | 客户来自英语发达国家，医疗服务目的地为中国 | 首批中国城市、具体客户国家与支付币种待 R01 |
| 服务收费 | 定价购买，医疗项目不同可对应不同的平台服务价格 | 产品组成项、数量、适用范围及价格由产品配置 |
| 包含费用 | 陪诊费、一次接机及一次送机、标准行程酒店与医院往返交通 | 酒店、医院和机场覆盖范围待产品约定 |
| 排除费用 | 客户自发行程产生的费用不包含 | 医疗费、住宿及其他费用归属需明确展示 R02 |
| 接受服务人 | 可替家人购买，每单一人；无平台统一就诊次数或天数上限，以产品约定为准；支持临时增加陪诊项目 | 按产品组成项加购，通知后续全部相关环节 |
| 现场服务 | 预约、挂号、翻译、取药、进入诊室及医疗材料代办等均包含；有责任风险的事项不包含，例如手术签字 | 建立可执行的职责清单，不能由软件自行判断所有责任风险 |
| IM | 早期不自动收发，以后接入企业版 | 首期人工沟通与事实记录，后续独立接口阶段 |

建议将医疗资源信息与平台服务商品分别建模；医疗项目影响平台服务价格，但并不由此推断医疗费已包含。诊疗由医疗机构负责，平台人员不替客户作手术签字等责任决策；这是已确认服务边界的实现方向，非法律结论。

### 2.3 规模与约束登记

开发前填写：注册用户、日活、峰值在线、读写请求峰值、资源条数、每日订单、每单任务数、附件日增量、AI 并发、运营国家、团队规模、预算和预计增长。各指标分别填写，不能用累计用户数代替负载。

建议按普通日、活动峰值及未来一年三个场景估算，标明估算来源；据此决定部署与扩容，避免先承诺微服务或多地域架构。已确认早期用户少于10000人、每日订单个位数。用户数不能推导峰值查询、资源量或附件量，其他容量与预算仍待 R11。

## 3 参与者 组织与权限建议

### 3.1 身份关系

建议区分账号、客户档案、实际接受服务的人、组织、工作人员和订单参与关系。已确认付款账号可以替家人购买，每个订单只关联一个接受服务人；同一订单可在所在地多次就诊。建议购买人与接受服务人分别保存；家人资料授权方式、工作人员所属组织仍待细化。

原文角色为游客、常规用户、陪诊师、客服、医疗资源数据管理员和客户管理员。已确认人工资源由数据专员维护、数据经理审核；爬虫资源由独立 AI 审核，默认无需人工审核，审核不通过标红；敏感代操作由相关审批人员批准，例如客服经理。建议另设系统管理员，负责配置与角色授权，不自动获得全部客户敏感资料访问权。

### 3.2 权限矩阵

| 操作与数据 | 客户 | 客服 | 陪诊师 | 资源管理员 | 客户管理员 |
|---|---|---|---|---|---|
| 浏览已发布资源 | 可 | 可 | 可 | 可 | 可 |
| 修改资源并发布 | 不可 | 不可 | 不可 | 人工数据专员编辑、经理审核；爬虫走 AI 审核 | 不可 |
| 查看订单与客户资料 | 本人或获授权订单 | 被分配客户 | 被分配服务的必要字段 | 不可 | 按管理范围 |
| 修改客户资料 | 本人可编辑字段 | 有效代理授权范围 | 限现场服务记录 | 不可 | 按职责与审计规则 |
| 推进任务 | 本人允许确认的节点 | 分配且授权节点 | 分配的履约节点 | 不可 | 按异常处理权限 |
| 修改报价或退款 | 发起申请 | 发起或审批分离 | 不可 | 不可 | 须单独授权 |
| 导出敏感资料 | 按本人数据范围 | 默认不可批量导出 | 不可 | 不可 | 单独授权与审计 |

游客建议仅能浏览公开资源。后台每次请求均校验角色、组织、订单关系和字段权限；页面隐藏按钮不构成权限控制。调换客服或陪诊师后撤销旧分配权限，并记录交接。

### 3.3 客服受托代操作

原文要求支持用户在线操作托管给客服，包含 IM 发照片、客服代录入行程。已确认原文应为“客户不想填表”。敏感操作也可代办，但必须先经相关人员审批，例如客服经理。

建议建立授权记录：授权人、代理人或代理团队、订单、允许操作、字段范围、有效期、撤回时间。代理操作记录真实操作者与被代理客户，禁止伪装成客户登录。

一般资料录入建议在有效客户授权范围执行。敏感操作必须先审批再执行；内部审批不自动代替客户授权。建议申请人和审批人分离，记录申请原因、动作、对象版本、金额、审批人及执行结果。批准后若金额、对象或动作改变，应重新审批；驳回、失效或未审批均不能执行。具体审批矩阵待 R06。客户撤回后，后续代理操作立即停止；已经完成的操作保留历史。

## 4 业务领域与核心对象建议

| 对象 | 定义及关系 | 关键约束 |
|---|---|---|
| 医疗机构 | 国家与城市下的机构，可关联多个医疗项目与医师 | 记录来源、审核、更新时间与发布状态 |
| 医疗项目 | 机构提供的医疗资源信息 | 与平台服务商品分离，可关联不同的服务价格；医疗费归属待明确 |
| 平台服务商品 | 可购买的单体产品或由多个产品递归组成的组合产品 | 保存组合树、引用产品版本、同级执行顺序、数量、价格及履约模板；根订单所购内容一次付清 |
| 加购记录 | 原订单下的额外产品组成项 | 独立价格支付快照、调整事件、后续环节通知与回执 |
| 账号与客户档案 | 登录身份与服务资料 | 购买账号与接受服务人分开，每单一人，支持家人代购 |
| 服务订单 | 组合树中的订单实例；根订单管理一次购买，子订单对应所购子产品 | 购买时与产品组合结构同构，固定条款、价格及商品快照；根订单统一支付退款，子订单记录各自履约及三段富内容 |
| 订单引用关系 | 一个订单指向另一个订单的具名关联 | 独立保存来源订单、目标订单、关系名称与描述；与父子包含关系分离 |
| 订单组 | 按顺序组织并描述一组订单，如行程计划、医旅攻略 | 只关联订单，不包含订单组；成员关系与交易及履约归属分离 |
| 订单组成员 | 订单与订单组之间的关联记录 | 保存组、订单、顺序及编排说明；成员权限不替代订单权限 |
| 支付与退款 | 外部支付记录及资金动作 | 独立状态，与订单关联，唯一交易标识 |
| 任务单 | 订单任务树的根任务，本身也是任务 | 根节点计第1级，当前默认最大深度3级；根层级计数为本文采用口径 |
| 任务 | 树中任意节点，可包含子任务 | 内容区、预估时长、乐观预估耗时、悲观预估耗时、常规耗时（基于历史数据）、费用、是否可加购；另记负责人、状态与版本 |
| 攻略版本 | 根据地区、机构、客户与订单生成的内容 | 来源、生成时间、生效版本、审核与差异 |
| 行程段 | 去程、接送、酒店衔接、就诊或返程安排 | 存时间点和当地时区，不混用出发与到达 |
| 服务分配 | 客服、陪诊师、司机等与订单的关系 | 生效期、交接、冲突与授权范围 |
| 授权与附件 | 客户授权和上传资料 | 敏感等级、所属对象、可见范围、保留策略 |
| 反馈与异常单 | 阶段建议、投诉或履约问题 | 负责人、处置记录、关闭条件 |

关系建议：一棵组合订单树由根订单统一管理交易，每个订单节点有自身履约内容；根订单的一份总任务单汇集各子订单对应的履约任务，子订单任务单可作为对应子树的视图，不重复创建同一履约事实。产品包含关系、订单父子关系、订单引用关系和订单组成员关系分别保存。多次就诊对应多个陪诊阶段；每个订单节点可有多个行程段；支付尝试和退款记录统一关联根订单及相应费用来源。每单一个接受服务人；多次就诊必须记录各次任务和安排，不能按次数生成多人订单。一次接机加一次送机，标准行程酒店与医院往返交通包含；就诊次数与期限以各产品约定为准，支持临时增项。历史订单保留资源及商品快照，资源更新或归档不改写已经发生的交易事实。

## 5 端到端业务流程

### 5.1 购买与服务准备

| 步骤 | 原文行为 | 建议系统行为及完成条件 |
|---|---|---|
| 1 注册 | 常规用户注册 | 支持 Google、Apple；账号关联和恢复见第 6 节 |
| 2 检索选购 | 检索机构或服务 | 区分医疗资源选择与付费商品；显示服务范围、价格与可用性 |
| 3 付款建单 | 付款后订单与任务单创建 | 建议先创建待支付订单，再由可信支付确认激活任务单；失败保留可追踪记录 |
| 4 初步沟通与服务确认 | 邮件、电话、添加微信或 WhatsApp | 已确认付款后平台与客户确认服务；双方确认之前取消可全额退，确认后开始按阶段产生费用；记录确认内容与时间，联系失败不视为完成 |
| 5 确定行程 | 用户填写、图片识别或客服录入 | OCR 生成候选字段，由客户或授权客服核对后生效；记录资料来源 |

建议购买前校验服务地区、日期、接待能力与该阶段所需资料。护照具体采集时点尚未确定，不默认强制在付款前上传。已确认直接定价购买，不同医疗项目可有不同平台服务费；购买前的可用性校验是建议实现，不增加必经人工询价环节。不能在未确认资源可用时把服务保证写入系统。

### 5.2 地接流程

保留原文顺序：提前一天确认；出发前一小时再次确认；到达后联系客户并确认等待点及识别特点；联系司机并确认车辆信息；司机接到后回报或读取已接通的打车状态；客户确认上车；抵达酒店后确认；一小时后确认就诊安排与所需物品材料。

建议每一步生成有负责人的任务，记录计划时间、实际时间、联系结果和证据。客户人数、衣着、车牌等只向相关服务人员短期开放，保存期限待定。司机反馈与客户反馈不一致时生成异常，不能直接完成接送。

已确认去程一小时前与返程四小时前以相应交通工具的开车或起飞时间为准；具体行程段需显式关联，不能混用航班和接送车时间。酒店后一小时应以实际到达且确认的时间计算。原文通知链接需进入相应任务节点；节点被变更或用户无权访问时，应显示当前有效安排或权限提示。

### 5.3 陪诊现场流程建议

已确认陪诊包含预约、挂号、翻译、取药、进入诊室与医疗材料代办等；有责任风险的事项不包含，例如手术签字。以下为该范围下的候选执行步骤：

1. 服务前确认医院、日期、出发时间、见面点、陪诊师、联系方式及客户需携带资料。
2. 双方到场后确认身份与会合；迟到、无法会合或人员缺席进入异常处理。
3. 根据购买内容协助找到科室、完成到院导航及约定的手续协助。
4. 在客户授权范围内提供语言或流程协助；执行已购买的翻译、进入诊室和材料代办协助；遇到手术签字等排除事项，停止代办并交由客户或适当责任人处理。
5. 记录已经完成的服务动作与后续安排，不由系统推断诊疗结论。
6. 向客户说明下一步安排；客户确认本次服务完成，或登记争议。
7. 如有下次就诊，生成新阶段；如服务结束，进入返程或结束确认。

服务资格、医疗机构现场允许的操作、等待与超时规则仍需细化；“责任风险”须转成员工可判断的明确排除清单。

### 5.4 返程与回访

原文要求录入返程，提前一天确认，出发前四小时再次确认，飞机旅程到达机场应至少留两小时；陪诊完成一天后回访。

建议区分航班起飞、离开酒店、接车和到机场时间。机场到达目标基于航班时间与可配置提前量计算，再根据交通预计时间生成接车安排。“两小时”保留为原文要求，但是否按机场或航班调整待确认，不能仅凭固定提醒推断客户一定能赶上航班。

已确认回访针对整单，整单服务完成一天后生成回访待办。回访失败记录再次联系待办；收集反馈、异常和投诉，给客户查看处理进展。

### 5.5 异常与补救建议

| 情况 | 用户反馈 | 系统与人工处理 |
|---|---|---|
| 重复付款或回调 | 显示已有支付结果 | 去重；核对多笔实际资金，进入退款或人工处理 |
| 已付款但任务单未创建 | 订单显示准备中 | 重试创建并告警；不得再次收费 |
| 航班延误或取消 | 展示最新安排与待确认变更 | 取消旧提醒，重算未完成任务，通知负责人 |
| 联系不上客户 | 显示待回应 | 按运营期限升级，不默认服务已经完成 |
| 陪诊师或司机缺席 | 显示异常及联系入口 | 寻找替换、交接与通知；是否退款按政策 |
| 医院临时变更 | 展示变更来源与确认要求 | 客服核对，重新安排依赖任务 |
| 服务争议 | 可提交描述与材料 | 异常单独立处理，不以客户未确认强制结单 |
| 外部 IM 或支付不可用 | 说明当前状态与替代渠道 | 保留任务、人工联络或等待核对 |
| 紧急情况 | 提供已批准的应急联络方式 | 按地区运营方案处理；流程须上线前明确 |

## 6 功能与交互要求建议

### FR01 身份与账号 已实现

用户确认登录相关能力已实现，本轮跳过登录方式与恢复流程重设计。现有身份模块作为订单、资料授权及后台权限的依赖；新增功能仍须校验账号、订单参与关系和工作人员权限。本文不宣称已经审计或验证现有实现。

### FR02 资源检索与维护

原文包含关键词、医院类型筛选，机构和服务检索及医院 CRUD。建议增加国家、城市、项目和语言筛选，实际首版筛选由数据质量决定。说明匹配字段、排序、分页、空结果与条件保留；推荐和商业推广须与普通结果区分。

已确认资源来自爬虫与医疗资源数据专员；爬虫按小时更新，由 AI 审核，默认无需人工审核，未通过标红；人工数据按周更新，由医疗资源数据经理审核。资源审核 AI 与客户答疑 AI 是两个职责独立的模块，前者可写审核结果，后者仍只读且无业务写权限。

已确认爬虫审核失败候选不公开，后台标红；保留上一次通过的公开版本，无历史通过版本则暂不公开。建议区分抓取时间、审核时间与公开生效时间，通过版本自动发布并保留来源；审核超时或接口错误属于审核异常，不能自动算通过。

记录来源链接、抓取时间、字段差异、审核规则与模型版本、审核结果及理由。AI 审核是质量判断记录，不标注为人工核实或机构保证；无变化数据可按版本复用审核结果。爬虫与人工字段冲突建议保留两种来源并明确优先策略，待 R08。详情显示来源、更新时间、机构关联、服务适用条件及联系信息。建议采用草稿、待审核、已发布、已归档流程；变更可追踪，误删可恢复。尚有订单关联的资源归档而非物理删除。

验收：未发布数据不出现在公开检索；筛选组合结果一致；机构归档后历史订单仍可查看快照。

### FR03 商品 订单 支付与退款

已确认定价购买，不同医疗项目对应的平台服务费可不同。购买页展示产品约定的陪诊范围、就诊次数或期限、标准交通覆盖、价格币种和取消规则；不默认全部产品无期限无限服务。金额由服务器计算。

已确认产品可配置每一步的费用，客户需要哪一项就加购哪一项；购买产品时一次付清所购内容，阶段费用不代表客户分阶段付款。已确认产品可以是单体，也可以由多个产品递归嵌套构成组合产品；组合节点是产品，不仅是一个产品内部的任务步骤。建议组成项保存节点标识、父节点、引用产品及其版本、同级顺序、名称、包含动作、数量单位、价格币种、适用地区、依赖、履约模板与退款分摊规则。发布或购买时固定完整组合版本，同一个子产品可在不同组合位置复用，每个位置有独立节点标识；展开后的每个节点仍只有一个父节点，递归引用不得形成组成循环。客户可见组成项购买价格；原单内部阶段费用占比仍不公开，两者不能混为同一字段。

已确认组合产品由根订单统一收取所购内容费用，子订单不独立支付或发起退款交易。建议子订单保留可追溯的费用分配和履行记录，统一在根订单核算退款；部分子服务取消只影响相应范围，是否允许及扣费口径仍按 R03—R05 细化。订单引用和订单分组本身不新增应收金额、不重复计费、不合并已有独立订单的支付记录。

加购关联原订单与同一接受服务人，保存所选组成项、数量、价格版本、支付、客户购买确认、任务与安排变化。单次加购也一次付清本次所选内容，不改写原商品快照。已确认加购就是调整任务项，无需额外确认，生效后继续执行；不得将加购重新放回待二次确认状态。支付与敏感代理审批的现有规则仍适用，后续通知回执是人员协调记录，不是客户再次确认。

已确认加购须通知后续所有相关环节，以便尽快调整。建议支付成功后产生持久化加购事件，识别所有受影响的后续任务、预约、陪诊师、司机、客服、行程、攻略和提醒；有依赖的安排按顺序更新。已经完成的事实保留，不因加购回退。

首期企业 IM 未接入，系统对内部人员生成通知与待办，外部合作方由负责人联系并记录送达和确认。通知不等于调整完成：各责任人回执已收到、已调整或有冲突，客服查看整单调整进度；发送失败重试，未回执升级，加购不能因一个通知失败丢失。临近行程加购优先处理；若无法安排则反馈客户并按批准规则处理，不能静默承诺。

订单、支付、退款分别建模；支付回调验真并去重，晚到回调进入核对。以下取消原则已经确认：购买付款时已完成购买确认，所购产品费用一次付清；付款后平台联系客户进行二次确认。沿用上一轮规则，二次确认之前可全额退款；二次确认之后随服务推进逐步形成应扣费用，即使尚未出行也可能不再全额退。应扣阶段费用从已付金额中核算，不是再次收费。此规则取代上一版“出发前免费取消”。改期默认免费保持不变。

#### 购买确认 二次确认与退款核算起点

已确认购买确认发生在付款环节，建议保存客户接受的产品、价格和条款版本及付款结果；付款后增加“已支付待二次确认”与“二次确认完成筹备中”状态。另行保存二次确认发起、完成时间、内容版本与双方确认依据；单方联系、邮件发送或客服内部勾选不建议视为二次确认完成。具体二次确认记录形式待 R04。

购买时确认产品和付款；二次确认建议核对接受服务人、需求、行程与执行安排，并再次说明适用的取消规则。二次确认后开始记录内部费用履行进度，客户仍无需再次付原产品费用。建议以实际完成的阶段作为退款扣费依据；每个产品的节点费用在编辑产品时配置；部分完成时怎样计入退款仍待 R04，不能从一次付清推断确认后立即全额不退。

#### 内部费用阶段

已确认费用由产品编辑配置到任务步骤，不需要为所有产品统一规定比例。以下只是候选任务分组，实际节点及费用以各产品发布版本为准：

| 阶段 | 可证明的计费里程碑示例 | 建议记录 |
|---|---|---|
| 二次确认 | 二次确认完成；内部退款分摊是否占比待配置 | 二次确认内容版本、依据、时间 |
| 服务筹备 | 完成约定的预约协调、攻略与人员安排 | 实际工作成果、完成记录、负责人 |
| 到达与接机 | 已实际完成接机阶段 | 行程、接到确认、接送记录 |
| 陪诊与就诊交通 | 每次约定陪诊或交通实际完成 | 本次服务范围、完成依据 |
| 返程送机 | 送机阶段完成 | 送达确认与服务记录 |
| 其他产品阶段 | 仅产品明确包含的阶段 | 对应完成条件与证据 |

内部费用占比与客户进度条分别建模；如采用费用占比，去重后的实际计费节点占比总计100%；如直接配置金额，由节点金额计算分摊，父子汇总不重复计入。内部退款分摊不展示给客户，不进入客户 API 或答疑 AI；客户仍应获得取消规则、退款金额及必要的扣费事项说明，具体文案待批准。订单保存购买时费用配置版本，增项保存自己的配置；后续改价不追溯改写旧订单。

#### 退款计算与冻结

候选计算：退款剩余额度＝该付款单元实收金额－已确认应扣阶段费用－已退金额。二次确认前应扣为零，按剩余已付金额全额退；二次确认后按有效阶段记录计算。金额不得小于零或超出未退余额，逐阶段舍入后最后一阶段校正，币种不混算。手续费与外部实际费用不得擅自额外扣除，须有明确批准规则。

建议取消请求记录收到时间及当时确认、服务、费用版本；暂停后续未必要履约与计费，以该时点以前真实发生的服务事实核算。已在进行中的现场服务先安排客户安全交接，处理到什么程度计费需明确，不默认继续产生全单费用。不能在客户申请取消后补点任务完成来增加扣费；晚补录事实须有实际发生时间、证据与经理复核。

退款预览、申请、审批、执行和资金核对分开。审批记录绑定金额、阶段及订单版本；对象改变重新审批。改期沿用已履行事实，不把相同筹备工作重复扣费；平台无法履约等异常单独处理，不直接套用客户主动取消政策。阶段部分完成、二次确认与取消并发、加购退款、平台原因取消规则见 R03—R05。

验收：重复回调不重复订单或退款；二次确认前全额退；二次确认后且未出行仍按真实已计费阶段扣费；取消后不得无依据增加费用；原单与增项分别核算；费用占比不泄露；累计退款不超过实收。

### FR04 任务单 攻略与进度

#### 产品组合树 订单组成树与履约任务树

已确认产品与订单在组成结构上同构：单体产品生成一个订单节点；组合产品按所购版本递归生成根订单与子订单，保留父子结构和执行顺序。同构指购买时所选配置的组成结构与订单实例结构对应，不要求产品与订单使用同一标识、字段、状态或数据库表。订单加购及个性化调整可以形成新的实例版本，不反向改写产品模板。建议保存产品组合节点与订单节点的映射、根订单标识、父订单标识、同级顺序、来源产品版本与内容快照，便于追溯。

产品组合树表达“服务由哪些产品组成”，履约任务树表达“服务怎样完成”；两者不能直接等同。一个子产品可有多步任务，普通步骤不因此获得独立交易身份。建议在根订单任务单中按产品组合树展开各订单节点对应的履约子树，保存任务所属订单节点和来源模板。父子订单汇总状态与子树任务状态须一致，同一服务不在两个任务单中重复执行或计入费用。

已确认执行按顺序进行。建议每层按明确的同级顺序执行，一个子树达到完成或已批准的取消／不适用条件后，再进入下一个兄弟子树；容器节点负责汇总，其自身需要执行的动作应定义为明确步骤，避免容器与子节点重复执行。前置描述是准备说明，后置描述是完成后说明，不作为自动状态转换依据。顺序、显式依赖和实际预约时间冲突时提示调整，不静默改变顺序；本版不把并行执行作为已确认能力。

下述默认3级限制继承自既有任务配置，仍按根计第1级。产品组合的数据模型应支持递归扩展；组合深度与展开后的任务深度分别校验，不能只校验被引用子产品自身的深度。产品组合深度上限、节点数量上限，以及与现有任务深度配置的配套方式待 R12；不能把无限扩展能力解释为当前编辑器已经不限深度。

#### 产品任务模板与订单任务实例

已确认每个产品有自己的服务流程，即任务单；任务单本身也是任务，是根节点。任务可嵌套，结构本质为树；模型支持任意深度扩展，当前默认限制3级。本文暂采用根节点为第1级的计数口径，即根任务→子任务→孙任务；如业务原意是根下再允许3级，应调整该配置和验收口径。

每个节点均可在产品编辑中设置内容区（描述、图片、攻略等）、预估时长、费用及是否可加购。建议节点另保存标识、父标识、同级顺序、负责角色、完成条件、依赖及内容版本；父子关系表示包含，前后依赖单独定义，树的上下层表示包含；本版以同级顺序和子树完成条件定义先后，不能仅凭父子关系推断执行时点。

产品保存可版本化任务模板，购买时实例化为订单任务树，保存产品及节点快照。产品后续编辑不静默改写现有订单；订单个性化内容与实际执行记录存在实例上。加购按所选任务项增加、重复或调整节点，保留变更版本；具体操作形式由产品配置，已完成记录不得覆盖。

建议编辑校验：每棵树只有一个根，非根有且仅有一个父节点，不允许循环或跨树父关系；插入、移动、复制和加购后的最终树均不得超过默认3级。预估时长用于计划与提醒，不代表实际完成或自动扣费。

#### 乐观预估耗时 悲观预估耗时与常规耗时

已确认每个任务节点新增两个独立属性：乐观预估耗时、悲观预估耗时。适用于根任务及各级子任务，在产品任务编辑中配置，随模板版本保存并进入订单任务实例快照。已确认常规耗时默认由系统基于历史实际执行数据自动统计计算，与乐观及悲观预估独立记录，不要求运营人员手工填写。原有预估时长暂保留为既有字段，迁移或删除规则尚未确定；不能直接把它改名为历史常规耗时，也不采用乐观悲观值的平均数代替历史统计。

| 属性 | 建议字段 | 含义 |
|---|---|---|
| 乐观预估耗时 | optimistic_duration_minutes | 条件顺利时预计完成任务所需时间 |
| 悲观预估耗时 | pessimistic_duration_minutes | 在合理不利条件下预计完成任务所需时间，不是绝对最长保证 |
| 常规耗时 | typical_duration_minutes | 默认由系统基于同类任务历史实际耗时自动统计计算 |

常规耗时的计算方式以下为建议：采用可比较、已完成任务实际耗时的中位数，按任务模板节点或稳定业务类型归集；必要时区分城市、机构与服务类型。模板节点需保留跨版本可追踪标识，任务被复制或加购后仍可关联到同类历史数据；内容或执行范围实质改变时不能直接沿用不可比样本。

保存统计值、样本数、统计时间窗口、更新时间、分组条件与算法版本。取消、未完成、缺少起止时间及明显错误记录不纳入；异常长耗时需标记原因，不能为了缩短统计值而直接删除真实延误。具体样本门槛与窗口由配置决定，初期样本不足显示“历史数据不足”，不得生成伪造常规值；安排仍可参考配置的预估耗时。

实际耗时建议以任务实际开始至完成的经过时间计算；若需扣除暂停，另行定义净工作耗时并记录暂停区间，不能混用统计口径。根任务或父任务采用自己的实际起止时间，包含实际等待和间隔，不能直接用子任务耗时之和替代。

常规耗时默认由系统自动统计更新，产品编辑页展示只读结果与样本依据，默认不提供手工覆盖入口；人工配置的乐观、悲观预估与系统历史统计分别存储。建议任务完成或实际时间更正后触发对应分组重算，并以周期任务补算；失败保留上次有效结果、显示更新时间并重试，不将失败结果写为0。订单保留当时用于计划的统计快照，最新历史值可另行展示，不静默改变已约定时间。常规耗时可以落在乐观悲观区间之外，这应提示复核预估配置，不能强制裁剪历史结果。统计更新不自动推进任务、改变费用或触发退款扣费。

建议统一以分钟存储，界面可显示小时或天；已填写值不得为负，乐观值不得大于悲观值。不确定时保留为空并显示未估算，不能用0代替未知。是否必填由任务模板发布规则决定；无实际耗时的容器节点可按明确规则配置为0或采用汇总。

两项可用于展示耗时区间、安排缓冲及任务延误提示，实际开始与完成时间另行记录。不得因到达悲观耗时就自动认定任务完成、取消、收取费用或触发退款扣费。父任务估算不能直接把自身与所有子节点重复相加；本版串行执行可按实际执行路径累计子任务估算，并单独计入必要等待、交通和预约间隔；不能把仅有说明内容的容器耗时再加一次。若未来引入并行，须另行确认调度与统计口径。具体时间调度策略为建议，不是已批准规则。

验收：所有层级可配置两项预估并关联历史常规耗时；历史统计值可追溯样本口径，样本不足显示未知；乐观值大于悲观值时拒绝保存；未知与零可区分；订单快照不被后续产品修改覆盖；估算耗时变化不自动改变履约状态和费用。

#### 父子进度 费用与内容

父任务的内容区可展示总攻略与说明，子任务可有各自描述、图片及攻略；客户、客服和陪诊师从同一树实例读取各自可见内容。内部字段与公开内容分开，不能通过内容区或图片暴露内部退款分摊。

建议父任务进度按适用子任务汇总，关键父节点另有完成条件；加购后重新计算未完成部分，保留历史版本。加购导致分母变化可以改变显示进度，但不回退已经完成节点的真实状态。

每个节点费用可配置；建议区分节点自身计费金额与子树汇总金额，父层显示汇总不重复计费。订单金额由实际计费项计算，退款根据生效的计费节点和实际履行记录计算；节点类型、是否自身计费与子树计费须校验，避免父子费用重复扣除。原单内部占比、客户可见加购价格分别保存。

根任务关闭条件建议为所有必需任务完成或有记录的取消/不适用处理，不能通过直接勾选根任务跳过未完成服务。产品任务模板发布前验证内容、节点费用、加购资格、深度与依赖。

原文要求分段、进度、客户推进、客服可见、多角色更多信息、持续更新及每步反馈。

建议每个任务包含：阶段、标题、说明、责任人、依赖、计划时间、期限、完成条件、客户操作、内部说明、状态与历史。进度按适用任务计算，取消和不适用不应伪装成已完成；是否加权须明确。

客户只能确认允许其确认的节点；关键履约节点须由负责人核验，不能通过客户点击直接证明司机已完成接送。已确认“必须”指客服必须询问客户对前一步的意见或建议，客户可以回答“无建议”，也可以不回答；不阻断后续服务。建议记录询问时间、客服、渠道、客户回答或未回应；客服发出询问即完成询问义务，客户回答状态独立记录。系统可生成询问待办，不能以生成待办代替已实际询问。

资料变化时：保存新版本，定位受影响的攻略和未来任务，生成差异；已完成任务保留当时事实。确定字段如航班号可同步，关键安排与个性化攻略文本建议人工审核后生效。AI 答疑查询不能修改攻略或任务状态；自动更新由业务规则与审核流程负责。对已确认安排的实质变更需通知并重新确认，不能静默覆盖。

验收：同一任务被同时修改会提示冲突；更改行程不会篡改历史；所有角色看到同一生效版本，内部信息不会泄露给客户。

#### 订单引用关系

已确认一个订单可以引用另一个订单，引用关系可以添加名称和描述。例如“后续复诊”“关联接送”，名称和描述属于该关系，不改写被引用订单自身的标题或内容。建议关系字段包含标识、来源订单、目标订单、名称、描述、创建者、版本与可见范围；关系描述可采用富内容。

建议引用仅表示关联：不复制目标订单，不改变其父子归属，不自动推进状态、创建任务、产生费用或合并退款。若关联确实要求执行依赖，须另建明确依赖与完成条件；不能把一条说明性引用直接解释为必须先完成目标订单。

创建与读取关系均检查来源和目标订单权限；客户不能通过引用查看未授权订单。目标归档后保留历史关系与必要快照，权限撤回后显示受限状态，不泄露内容。引用可能形成图，树的单父节点约束不适用于引用；遍历采用已访问集合与深度／数量限制，避免循环展开及同一目标重复计入攻略。是否禁止自引用和循环引用、删除关系规则及跨客户引用范围待 R13，本文未擅自要求所有引用都无环。

#### 订单组与三段富内容

已确认支持订单组，用于组织和描述一组订单，例如行程计划、医旅攻略；暂不支持订单组嵌套。建议保存组标识、名称、富内容描述、所有者、用途、可见范围、版本，以及有序成员列表。组成员只能是订单，不能是其他订单组；分组用于编排，不成为额外收费订单或改变既有履约归属。组内顺序用于攻略组织，不自动覆盖成员订单树内部的执行顺序；如要求跨订单强制执行依赖，须单独定义并校验。

建议订单组通过成员关系复用订单，同一个订单可以参加不同用途的组；增删成员或改序不改变订单事实。若将组合根订单及其子订单同时加入一个组，展示和生成需按订单标识及组成范围去重，不能重复履约、计费或叙述。同组是否允许混合不同接受服务人、不同权限及已完成历史订单待 R14；仅凭组访问权不能获得所有成员订单的访问权。

已确认每个订单节点，包括根订单与各级子订单，均提供以下三个独立富内容字段。产品模板可设置默认值，购买时形成订单快照；订单实例可在授权范围内个性化修改，不反向改写产品。支持字段不等于强制每项必须非空；内容格式、空值规则和发布要求以下为建议，待详细规格确定。

| 字段 | 建议字段名 | 用途 |
|---|---|---|
| 前置描述 | pre_description | 服务开始前的准备、材料、到场条件及注意事项 |
| 描述 | description | 服务综合说明、服务进行时的步骤与现场指引 |
| 后置描述 | post_description | 服务完成后的注意事项、后续工作及下一步衔接 |

建议三项统一支持文本、列表、图片、链接与受控附件；保留内容版本、作者、修改时间与可见范围，校验富内容与附件权限。原有订单综合描述迁移到 description；前置和后置字段无来源时留空，不编造准备事项。任务节点原有内容区保留，订单三段内容与任务说明明确归属，避免同一说明复制后无法同步。

#### 基于真实订单生成连续攻略

已确认可通过真实订单组合生成更符合实际情况的攻略或指引。建议按订单组顺序、订单组成顺序及有效行程，将每个订单的前置描述、描述、后置描述串联；子订单内容按执行位置展开，父订单综合说明仅出现一次。前一步的后置工作与下一步的准备可合并衔接，合并结果仍可追溯来源，不能遗漏条件或把不同人的安排合为同一行程。

顺序用于表达服务先后，具体时间依据已核对行程与实际记录。生成时区分计划、已确认安排及已完成事实，检查预约冲突、交通间隔、材料缺失和内容矛盾；发现缺口列为待确认，不凭空生成医疗方案、医疗注意事项或尚未落实的预约。历史真实订单可作为流程依据，不能直接承诺同样价格、人员、耗时或资源仍可用。

订单引用仅在相关且有权访问时辅助说明，不默认递归吸收全部关联订单。建议攻略保存订单组版本、有序成员、订单及内容版本、生成输入快照、事实与来源、生成时间、模型版本及审核结果；来源变化标记攻略待更新，历史版本仍可追溯。

生成器与 FR07 的只读答疑 AI 分离：生成器只返回草稿，不直接修改订单、任务、行程、支付或审批；保存、审核和生效由独立业务流程完成，关键安排与个性化文本沿用人工审核建议。生成仅接收经授权的行程、陪诊流程及相应三段说明；富内容混入病历、护照、内部费用或私人联系方式时先过滤，不因字段可编辑就全部交给 AI。若将真实案例生成可公开攻略，须另外脱敏并核实公开授权，私有订单组不自动公开。

验收建议：单体及递归组合结构正确实例化；顺序约束不被普通点击跳过；根订单统一支付退款且子树无重复费用；引用名称和描述独立保存，循环遍历有限终止且不越权；订单组不可嵌套，成员改序不改变交易；所有订单节点都有三项富内容字段；攻略按有效版本生成、父子与引用内容去重、缺失和冲突明确显示，生成器不能越权写业务状态。

### FR05 行程与图片识别

支持手动、OCR 候选和客服代录。OCR 应给出原图、候选字段及未识别项，时间、日期、时区、航班、姓名必须核对后生效。低置信度或失败转人工，不填入猜测值。

上传校验格式、大小和文件安全；附件关联订单和权限，下载使用受控访问。客户更正后追踪旧值、新值、操作者和影响任务。

### FR06 客服与陪诊工作台

客服可按分配、阶段、超时、异常和未联系筛选；查看客户授权资料、沟通摘要、有效攻略及任务。陪诊师查看自己分配的服务、必要资料、会合信息与可操作任务。建议显示下一动作、责任人、期限和最后更新时间。

原文要求未来沟通都在 IM。建议第一版允许人工沟通并把关键安排写回系统；除非接入明确支持的接口，不承诺自动抓取私人聊天。IM 不能成为订单状态的唯一来源。已确认早期不自动收发，后续接入企业版；首版不把企业 IM 自动接口计入交付。

### FR07 专属 AI 只读答疑与查询

已确认当前 AI 仅答疑和查询，不修改任何状态，不提供医疗建议；只向其提供行程与陪诊流程有关的信息。建议通过允许字段清单读取生效行程、服务安排、任务状态和可公开流程说明，输出来源与更新时间。AI 没有修改资料、推进任务、支付、退款、审批或发送消息的业务工具。

护照、病史、病历与内部退款权重不进入 AI 上下文。跨用户访问须在查询层验证，不能依赖提示词隔离。攻略随资料更新及按订单组生成草稿属于 FR04 的独立业务机制，不能绕过只读 AI 边界。

验收：客户答疑 AI 无业务写接口；不能读取其他客户数据、护照或医疗材料、内部费用占比；未知安排明确提示缺失或转客服；AI 故障不阻断履约。

### FR08 通知 反馈与后台

通知包含业务事件、对象、接收人、渠道、计划时间、去重标识和送达结果。原文订单邮件、行程确认和进度链接保留；渠道可用性与用户偏好待确认。发送成功不等于客户已读或确认。

后台建议包含模板、地区规则、资源发布、人员分配、异常单、反馈、授权、通知失败、支付核对和审计查询。退款与敏感导出单独授权。

## 7 状态 事件与并发规则建议

| 对象 | 候选状态 | 关键规则 |
|---|---|---|
| 订单 | 待支付、已支付待二次确认、二次确认完成筹备中、服务中、待结束确认、已完成、取消处理中、已取消 | 交易及二次确认状态由根订单管理，子订单不独立待支付或重复确认；子订单记录自身履约状态，根订单按必需子树和任务汇总；争议独立标记 |
| 支付 | 已发起、处理中、成功、失败、待核对 | 以支付渠道可信结果为准，不由客户页面决定 |
| 退款 | 已申请、待审批、处理中、成功、失败 | 与订单完成状态独立；部分退款记录金额 |
| 任务 | 未就绪、待执行、执行中、待确认、已完成、已取消、不适用 | 超期作为标志，异常关联问题单；前序子树条件与显式依赖满足才就绪 |
| 订单组 | 草稿、有效、已归档 | 只管理编排版本，不自动推进成员订单；不支持嵌套 |
| 攻略 | 草稿、待审核、生效、已被替代 | 生效版本唯一；保留历史和来源 |
| 资源 | 候选、待审核、审核通过、审核不通过、审核异常、已发布、已归档 | 审核与发布状态分开；爬虫 AI 未通过标红；失败候选不公开，保留上次通过版本 |

每个转换均定义触发者、前置条件、数据变化、事件、通知与失败补救。自动推进须以可靠事件为依据；时间到了只生成提醒，不能自动证明服务已经履行。

并发建议：写入携带对象版本，旧版本更新返回冲突并展示差异；支付、建单、创建任务单、发送通知使用幂等标识。退款累计金额不能超出可退余额。人员排班冲突在确认分配时重新校验，不能只在页面查询时检查。

## 8 数据 信息与协作建议

### 8.1 最小数据字典

| 数据组 | 最小字段 | 来源与权威归属 |
|---|---|---|
| 机构项目 | 标识、名称、国家城市、类型、地址、来源、审核、更新日期 | 资源模块；运营核实 |

| 商品订单 | 产品及组合版本、组合节点、父节点、根订单、同级顺序、服务人、地区、日期、金额币种、条款版本、状态、前置描述、描述、后置描述及内容版本 | 订单模块；组合结构与交易快照 |
| 订单引用 | 来源订单、目标订单、关系名称、描述、版本、创建者、可见范围 | 订单模块；具名关联，不作为包含或计费依据 |

| 支付退款 | 渠道、外部交易号、金额币种、状态、核对结果 | 支付模块 |

### 8.2 一致性与生命周期

建议交易与权限变更在权威存储内即时一致；搜索索引、报表和消息可延迟更新，允许延迟需设指标。每个模块只写自己拥有的事实，其他模块通过接口或事件读取。

时间存储同时保留时间点与地区时区；当地日期类数据不能盲目转换为 UTC 日期。金额存最小货币单位或固定精度及币种，不用浮点数。多语言名称与原文分开，翻译记录来源与版本。

上传、采集、核对、发布、使用、归档、删除各阶段明确责任人。账户注销不等于立即删除全部交易记录；按数据类别冻结保留政策，明确备份和第三方副本处理。政策尚待 R10。

### 8.3 分析口径

建议记录搜索、筛选、详情、购买发起、支付确认、任务推进、攻略更新、提醒结果、异常与反馈。事件带时间、对象、版本和去重标识，避免在分析事件中上传原始敏感材料。取消单、测试单、退款单如何计入转化和履约指标需统一定义。

## 9 模块 架构与接口建议

### 9.1 模块职责

建议分为身份权限、资源目录、商品订单、支付退款、客户授权、行程履约、攻略模板、通知、AI/OCR、运营审计、独立资源审核 AI 和分析。模块边界先通过代码和数据职责形成；首期可部署为模块化应用，负载与组织确有需要时再拆服务。

候选运行结构：网页与工作台通过后端接口访问业务模块；关系数据库保存交易和履约事实；对象存储保存附件；异步队列执行提醒、索引、OCR 与只读 AI 答复；搜索组件按数据量决定。缓存和搜索均可重建，不成为订单的唯一存储。

### 9.2 接口契约

| 接口能力示例 | 输入要点 | 输出与失败要求 |
|---|---|---|
| 资源查询 | 关键词、筛选、分页、语言 | 结果、总量或游标；非法条件明确错误 |
| 创建购买 | 商品版本、日期、服务人、幂等键 | 订单和支付入口；价格或容量变化要求重新确认 |
| 支付回调 | 验证后的交易事件 | 去重处理结果；状态冲突进入核对 |
| 修改行程 | 订单、字段、对象版本、代理身份 | 新版本和受影响任务；权限或版本冲突不覆盖 |
| 确认任务 | 任务、版本、确认动作与证据 | 状态及后续待办；依赖不足拒绝 |
| 维护产品组合 | 产品版本、组成节点、引用子产品版本、顺序 | 校验组成无环、展开深度与节点数量；发布固定版本 |
| 维护订单引用 | 来源与目标订单、关系名称、描述、版本 | 校验双方权限；不产生交易或自动履约 |
| 维护订单组 | 组版本、名称描述、有序订单成员 | 拒绝嵌套组；版本冲突不覆盖，不改成员订单状态 |
| 生成订单组攻略 | 组及订单版本、允许字段、受众、生成参数 | 返回带来源的草稿、缺口与冲突；事实变化须复核后生效 |
| AI 只读查询 | 订单参与关系、允许字段、当前事实版本 | 流程与行程答复；无任何业务写动作 |
| 敏感代办审批与执行 | 授权记录、动作、对象版本、审批记录 | 仅审批通过且仍有效时执行，保留真实操作者 |

正式接口说明应包含协议、认证、字段、错误码、限流、超时、版本兼容、幂等与审计。事件建议包含事件标识、类型、对象标识、版本、发生时间与关联请求；不传播不必要的敏感内容。

### 9.3 异步与外部依赖

数据库提交业务变化与待发事件应可恢复，避免已支付但事件永久丢失。队列按可能重复投递设计，消费者去重；重试有次数和间隔，最终失败进入人工处理队列。

提醒任务执行前检查最新行程版本、任务状态和有效收件人，避免改期后发送旧提醒。AI/OCR 超时可重试或人工处理；支付回调不能因通知供应商失败而整体回滚。每种外部服务明确超时、重试条件、费用、供应商限制与替代路径。

## 10 质量 安全与运行目标建议

已确认初期用户少于10000人、每日订单个位数，建议采用模块化应用加异步任务，暂不以用户规模为理由建设复杂分布式部署。以下指标仍为评审候选；资源数量和查询峰值未知，负载条件是测试假设，不代表实际流量。

| 能力 | 候选目标 | 验证前提与方法 |
|---|---|---|
| 搜索 | 后端 P95 不超过 1 秒 | 10万条已发布资源、100次请求/秒、连续30分钟；冷热场景分别测 |
| 订单任务读写 | 后端 P95 不超过 800毫秒 | 20次业务写请求/秒；不含外部支付和模型等待 |
| 搜索索引更新 | 99%在60秒内可见 | 从资源发布提交至查询可见，故障单独统计 |
| 任务进度同步 | 99%在5秒内可见 | 从事务提交至另一工作台刷新；弱网另测 |
| 提醒待办产生 | 99%在计划时间后60秒内生成 | 衡量内部任务创建，不把供应商送达算成系统保证 |
| 核心系统可用性 | 月度99.9% | 明确核心接口、统计窗口及维护计入规则 |
| 故障恢复 | RPO 15分钟、RTO 2小时 | 在约定故障场景恢复并核对订单、支付与任务；支付渠道再对账 |

安全建议包括：服务端身份和对象授权、后台多因素认证、传输与存储保护、密钥集中管理、受控附件访问、审计、上传检查、依赖漏洞检查和数据脱敏。反爬采用限流、异常行为识别、分级验证及滥用告警；阈值可配置，监测误伤，不承诺公开信息绝对无法抓取。

AI 输入、附件和检索资料视为不可信内容，不允许它们修改权限；答疑 AI 不配置任何业务写工具。资源审核 AI 仅通过限定接口写审核结果，发布由规则引擎执行，不能写订单、客户资料或履约状态。答疑 AI 仅接收行程与陪诊流程白名单信息；OCR 的材料范围须单独授权，不能因识别过材料就将其提供给 AI。

地区隐私、数据跨境与服务资质要求需在首发地区确定后专项核实；本文仅登记设计事项，未作法律结论。

## 11 运营 可观测性与维护建议

- 每个资源有数据维护人与审核人；每个服务订单有主客服和替补；每个现场任务有履约责任人；每个异常有升级路径。
- 展示支付待核对、任务创建失败、超时任务、通知失败、未审核攻略、资源过期和授权异常工作队列。
- 日志关联请求、订单、任务和事件，脱敏联系方式及材料；记录关键状态变更，禁止把完整医疗资料写入日志。
- 监测接口成功率与延迟、队列积压、支付核对差异、提醒滞后、权限拒绝和 AI 成本。告警带负责人、处理入口及升级时间。
- 定期备份并实际恢复验证；恢复后核对外部支付与业务记录，避免只验证数据库能启动。
- 配置变更记录版本、作用地区、生效时间和操作者。成本按存储、搜索、通知、AI、OCR和运行资源分别统计。

### 11.1 Q14 初期运营推荐方案

以下为面向少于10000名用户、每日个位数订单的建议，不是已批准的对外承诺。采用每单主客服、替补客服与值班经理，普通咨询定时处理，正在执行的服务按实际行程覆盖。少量订单阶段可人工排班，但必须验证值班人员能接电话并处理事务。

| 类型 | 推荐规则 | 超时与升级 |
|---|---|---|
| 普通人工咨询 | 中国时间09:00—21:00，每日；值班时段2小时内首次人工回应 | 非值班信息在下一服务窗口开始后2小时内回应，显示客户当地对应时段；根据实际国家分布增设窗口 |
| 付款后二次确认 | 付款时购买确认已成立；付款后1个运营工作日内发起二次确认，核对执行安排 | 客户未回复不得自动视为二次确认或启动二次确认后扣费；临近出行加急 |
| 服务中紧急协调 | 对已安排的航班、接送与陪诊窗口提供覆盖；5分钟内首次回应，10分钟未响应升级经理 | 主客服与替补同时可联络；夜间实际行程也须有值班，不依赖普通窗口 |
| 接机失联 | 核实实际落地、出关与约定会合时间，按IM及电话联系；超过约定会合时间15分钟仍失联升级 | 不能以落地时间直接算失联；司机等待、费用与后续措施另定 |
| 司机或陪诊师缺席 | 约定时间未到即联系核查；10分钟未解决升级经理，20分钟内向客户更新替代安排 | 无法履约记录明确事实，退款补偿另行审批 |
| 敏感操作审批 | 普通申请4个值班小时内处理；当日行程相关加急30分钟内回应 | 配置替补审批人；不能因超时绕过审批 |
| 退款申请 | 1个运营工作日内给计算结果与处理说明；资料齐全后2个运营工作日内完成内部审批 | 审批完成后及时提交支付渠道；分别展示审批、已提交及到账，到账时间按实际渠道显示 |
| 投诉 | 24个自然小时内首次回应，3个工作日内给处理方案 | 未能结案说明原因与下一次更新时间，不虚假标记解决 |
| 反馈询问 | 每阶段完成后询问前一步意见；无需客户回答才能继续 | 记录已询问、客户回答或未回应；客服遗漏进入补办队列 |
| 整单回访 | 整单服务完成24小时后产生待办，在客户可联络时段执行 | 联系失败记录一次结果，不反复骚扰 |

建议普通值班每天开放，所以“运营工作日”为每日；退款审批及投诉中的工作日需统一定义，可先按中国周一至周五、法定节假日除外。所有时限使用明确日历，不混用自然小时、值班小时与工作日。

每单保存客户当地时区和允许联系时段；非紧急消息建议在客户当地09:00—20:00发送，已约定行程提醒按需要发送。交班列出下一24小时行程、未确认服务、未解决异常、待审批及待退款；接班人确认后转移责任。

升级链建议为主客服→替补客服→值班经理，所有服务窗口有真人负责。对突发医疗状况，只规定员工启动已批准的当地应急联络和内部通知流程，不由AI或陪诊师作医疗判断。上线前完成联络与缺席、失联等桌面演练，再把可兑现的响应时间写入客户页面。

## 12 交付 发布与验收建议

### 12.1 阶段安排

1. 细则确认：全部功能首版交付范围已确定，继续冻结商品、标准行程、退款与任务细则。
2. 闭环开发：完成检索、身份、购买、订单、人工履约工作台、任务与权限。
3. 自动化增强：接入提醒、OCR、攻略版本和 AI；以人工兜底验证。
4. 上线验证：完成功能、跨角色、支付核对、权限、负载、恢复与运营演练。
5. 后续扩展：按数据与需求增加国家、语言、外部接口和服务自动化。

以上为内部实现顺序，不是缩减首版范围。首版包含全部已确认功能；企业 IM 自动收发按用户要求后续接入。登录复用现有实现。

### 12.2 验收覆盖

| 用例 | 必须观察的结果 |
|---|---|
| 正常购买到回访 | 所有角色完成各自任务，订单和进度一致，历史可追溯 |
| 重复支付回调与请求 | 订单、任务单与资金动作不重复 |
| 支付成功时异步系统故障 | 恢复后补建任务并告警，不丢订单、不再收费 |
| 多角色同时改行程 | 旧版本被识别，后续任务依据最终有效安排 |
| 行程改期后旧提醒到期 | 旧提醒不发送，新增提醒与新版本一致 |
| 客服授权撤回 | 后续代理写入被拒绝，审计仍可追溯 |
| 陪诊师换人 | 新人获必要上下文，旧人权限撤销 |
| OCR 日期或时区误识别 | 未确认候选不影响正式行程 |
| 客户答疑 AI 越权或事实缺失 | 无业务写能力，不读取护照、医疗材料或内部权重，提示缺失或转人工 |
| 敏感代办未经审批 | 执行被拒绝；批准后对象或金额改变需重新审批 |
| 客服反馈询问与客户未回应 | 客服必须询问并记录；客户无建议或不回答均允许，不阻断服务 |
| 爬虫 AI 审核 | 通过按批准策略发布，不通过标红，异常不视为通过；不影响客户答疑 AI 的只读边界 |
| 爬虫与人工更新冲突 | 保留来源版本，不静默覆盖人工核实字段 |
| 资源下架 | 公开查询移除，历史订单快照保留 |
| 退款与履约同时变化 | 资金和任务按批准政策分别更新，无超额退款 |
| 购买确认与二次确认 | 付款时购买确认留存；二次确认单独记录，原单不会重复收费 |
| 加购与跨环节调整 | 生效后只调整一组任务项，无需再确认即可继续执行；后续环节通知可追踪，失败可补发 |
| 任务树与层级限制 | 根节点是任务；默认根计第1级，最大3级；移动、复制、加购均不能绕过限制，无循环或多父节点 |
| 父子费用核算 | 父节点汇总与子节点自身费用不重复计入购买金额或退款扣费 |
| 单体与递归组合购买 | 产品组成节点与订单节点映射可追溯；根订单统一支付退款，旧订单不受子产品后续改版影响 |
| 按顺序执行 | 前序子树未达到有效完成条件时，后序不就绪；合法取消或不适用保留依据 |
| 订单具名引用 | 关系名称与描述独立；不改变包含关系、状态或金额；循环展开终止，权限撤回后不泄露目标内容 |
| 非嵌套订单组 | 只能添加订单；改序及移除不取消订单；根与子订单重复入组时攻略去重 |
| 三段富内容与连续攻略 | 根及子订单字段齐全；按成员与组成顺序生成，来源可追溯，变更标记待更新，缺口和冲突不被编造补齐 |
| 备份恢复 | 订单、支付、任务、附件关联及外部差异核对可用 |

质量目标须在约定数据和负载下测量。正式验收基线需包含需求编号、负责人、输入数据、预期结果、验证证据和批准人。

### 12.3 发布与协作

建议隔离开发、测试与生产；测试不使用未经授权的真实客户材料。数据库变更先兼容旧版本，迁移可核对，灰度观察后扩大。应用回滚不自动等于数据回滚，支付和客户操作不能直接撤销。

每个模块、数据集和接口有责任人；破坏兼容的变更需协调调用方。上线条件包含值班、告警、回滚、备份恢复和关键运营流程准备。发生未知资金状态时先核对，避免用回滚代码掩盖资金问题。

## 13 仍需确认的业务细则

用户已明确客户来自英语发达国家、中国为服务目的地；一次接机加一次送机与标准行程就诊交通包含；次数期限按产品、可临时增项；付款时购买确认、产品一次付清；二次确认前全额退、之后按实际阶段核算退款扣费；客服必须询问反馈，客户可不答；爬虫 AI 审核默认无需人工，未通过标红。以下仅列剩余细节。

| 编号 | 未决问题 | 建议 |
|---|---|---|
| R01 | 首批中国城市、客户国家及支付币种 | 按运营能力配置，不硬编码 |

| R12 | 产品组合深度和节点数量上限，与现有三级任务限制如何配套？ | 模型可扩展；组合与任务分别校验，编辑器实际能力明确展示 |

| R14 | 订单组跨服务人／跨权限规则，攻略私有与公开的发布流程？ | 成员权限分别校验；公开案例另行脱敏和授权 |

Q14 的推荐方案已写入第11.1节，仍属于建议，尚未被用户批准为对外服务承诺。

### 16.1 任务系统需要细化的事项

任务系统优先细化，因为产品、订单、攻略、进度、加购和退款均依赖它。至少需要明确：

- 产品组合节点、订单节点与履约任务怎样映射；组合深度与当前三级任务限制怎样配套。
- 按顺序执行时前序子树的完成条件、合法跳过、显式依赖和预约冲突怎样处理；并行作为未来变更另行确认。
- 根订单怎样统一支付退款，子订单怎样保存费用分配和取消履行记录。
- 具名引用的权限和循环处理、订单组成员顺序及去重、三段富内容版本和攻略生成审核怎样实现。
- 节点费用如何区分自身费用与子树汇总，避免重复计费。
- 正在执行的任务部分完成时，退款如何计算。
- 加购如何插入或调整任务，怎样重排行程、通知负责人、处理安排冲突。
- 常规耗时的统计口径、样本门槛、分组与更新频率。
- 产品模板更新后，已有订单采用旧版本还是受控迁移。

### 16.2 仍需冻结的业务与运行规则

业务上仍需确定：二次确认的有效记录形式、平台无法履约时的退款补偿、敏感操作审批矩阵、人工与爬虫数据冲突规则、护照采集方式和资料保存期限。第11.1节的运营时间与第10节的技术性能指标仍为建议，须结合实际人手、负载和预算评审。

### 16.3 建议下一步

先完成产品组合、订单与任务系统详细规格，用一个单体产品和一个组合陪诊产品验证映射及顺序执行。走通购买、加购、改期、取消退款和人员替换，再用真实订单组成一份行程计划，验证具名引用、三段富内容及连续攻略；记录规则缺口并修订，再据此设计页面和确定接口。
